# XKeen Hot Watcher 0.2.10

Обновление VLESS-подписки в **работающем Xray без `xkeen -restart`**.
Проект подготовлен для существующей схемы XKeen 2.x / Entware / Linux aarch64:
`/opt/etc/xray/configs`, файл `04_outbounds.main.json`, балансировщик `proxy`,
селектор `main--VL`. Это самостоятельный проект, не официальный компонент XKeen/XTLS.

**Статус проверки:** исходники собираются, автоматические тесты пройдены. В локальном
контейнере Xray 26.7.28 проверены API-переключение и выбор статического тега после
перезапуска; конкретный роутер и Destiny 2 с новой версией здесь не тестировались. Исходный ZIP репозитория
не является установочным пакетом: бинарники и их SHA256SUMS создаёт release workflow
после публикации нового Release с тегом версии. Проверки обновления программы —
[UPDATE_TEST_REPORT.md](docs/UPDATE_TEST_REPORT.md); прежние проверки подписки —
[TEST_REPORT.md](TEST_REPORT.md).

## Что делает программа

- Получает HTTPS-подписку в формате списка `vless://` или его Base64-представления.
  Trojan/VMess и прочие явно распознанные не-VLESS схемы исключаются. Поддержка конкретных
  параметров VLESS ограничена и проверяется строго: [форматы](docs/SUBSCRIPTIONS.md).
- Проверяет собранную конфигурацию установленным Xray. **До изменения рабочего процесса**
  проверяет доступность узлов через отдельные кратковременные Xray с HTTP-входом только
  на loopback. При стандартном выборе по задержке недоступные узлы сохраняются в
  списке, но не выбираются, если есть работающий ключ. Эти проверки не перезапускают
  основной Xray.
- Добавляет узлы через `HandlerService`, фиксирует выбранный outbound через
  `RoutingService`, сохраняет конфиг для следующей загрузки роутера.
- При каждой проверке подписки измеряет задержку успешного HTTPS-запроса через каждый
  VLESS-узел. Рабочий ключ сохраняется, пока другой не даёт заметного выигрыша и не
  истекло время удержания; при отказе ключа защита от частых смен не мешает переключению. Это меняет сервер для новых
  подключений; при желании можно выбрать прежнее поведение `selection_policy: sticky`.
- Независимо от загрузки подписки дважды проверяет активный ключ каждые пять минут.
  При двух отказах измеряет остальные сохранённые ключи и переключает на самый быстрый
  ответивший. Ручная команда `check-key` делает ту же проверку сразу.
- Сохраняет старые управляемые outbounds в памяти. **Автоматическое удаление отключено**:
  команда `gc` доступна после защитного периода, по умолчанию 30 минут.
- Работает службой: загрузка подписки каждые **1800 секунд**, восстановление сохранённой
  фиксации балансировщика каждые 60 секунд. Отдельная cron-задача не нужна.
- Использует блокировку, приватные файлы, журнал транзакций и журнал событий без URL/UUID.

## Автообновление самой программы

Отдельная служба `hotwatcher-updater` проверяет **подписанные** GitHub Releases, а не
персональную VLESS-подписку. Новая установка начинает в режиме уведомления. После
контролируемого bootstrap и первого подписанного patch-релиза администратор включает
автоматическую замену командой `hotwatcher update enable`. Во время замены останавливается
только Hot Watcher; основной Xray остаётся работающим. Ошибка запуска новой программы
возвращает предыдущий бинарник. Подробности и команды: [AUTOUPDATE.md](docs/AUTOUPDATE.md).
У установленного 0.2.4 команда `update check` может отклонить стандартное поле
`url` из GitHub Releases. Для первого перехода на 0.2.6 предусмотрен разовый
`scripts/repair-updater.sh` из нового архива; затем работает обычный updater.

**Что это НЕ обещает:** сохранение любой UDP-сессии, неизменность внешнего IP при смене
сервера, защиту от блокировки старого ключа провайдером или от прямого выхода при падении
самого Xray. **Это не kill-switch.** Подробнее — [ограничения](docs/SECURITY_AND_LIMITATIONS.md).

## Установка на твоём роутере

Устанавливай вне игровой сессии: включение API потребует **одного** обычного перезапуска.
Обычная работа Hot Watcher не вызывает `xkeen` и не меняет правила netfilter.
Исключение — ручной `hard-sync`, который временно останавливает и запускает XKeen.
Не удаляй старый `04_outbounds.json` с `vless-reality`, `direct` и `block`.

### 1. Скопировать и установить

Распакуй установочный архив из подписанного GitHub Release на компьютере в папку
`xkeen-hot-watcher` и скопируй её через WinSCP/SFTP, например в `/opt/tmp/`.
Выполни в **Entware shell**, где у тебя приглашение `~ #`:

```sh
cd /opt/tmp/xkeen-hot-watcher
sh install.sh
```

Установщик не скачивает зависимости, не правит routing и не трогает cron. Hot Watcher
остаётся выключенным до ручного включения; updater запускается в режиме уведомления.
Нужны уже установленный `/opt/sbin/xray` и системные CA-сертификаты.
Python, Node.js, jq и старый subscription-watcher для работы не требуются.

### 2. Отключить старое автообновление

```sh
sh scripts/disable-legacy-cron.sh
```

Сохраняется приватная резервная копия crontab. Удаляются только строки со старым
`xkeen-subscription-watcher`; например, задача `00 8 * * * /opt/sbin/xkeen -ug` остаётся.
Программа старого watcher пока остаётся на диске как резерв. **Не запускай оба updater-а
на один файл**, даже если у старого есть `--no-restart`.

Другие задачи с `xkeen -restart`, обновления самого Xray/XKeen и перезагрузка роутера
по-прежнему могут разрывать сессии — Hot Watcher их не отменяет.

### 3. Указать персональную подписку

```sh
sh scripts/set-url.sh
```

Вставь URL и нажми Enter. Он не попадёт в аргументы процесса или историю shell.
Ссылка сохраняется в блоке `hotwatcher.subscription_url` файла
`/opt/etc/xray/configs/07_hotwatcher_api.json` с правами `600`. Скрипт создаст API-фрагмент,
если его ещё нет; это **не перезапускает Xray**. Приватная копия в
`/opt/etc/hotwatcher/subscription.url` остаётся для уже установленного updater 0.2.4.
Не присылай эти файлы в диагностику. При ручном редактировании через WinSCP проверь:

```sh
chmod 600 /opt/etc/xray/configs/07_hotwatcher_api.json
/opt/sbin/hotwatcher doctor
```

Настройки: `/opt/etc/hotwatcher/config.json`. По умолчанию разрешён VLESS+Reality;
для VLESS+TLS см. параметр `allow_tls_nodes` и [ограничения конвертера](docs/SUBSCRIPTIONS.md).

### 4. Включить локальный Xray API

```sh
sh scripts/setup-api.sh
xkeen -xtest
```

Если в конце `Configuration OK.`, вне игры выполни:

```sh
xkeen -restart
xkeen -status
```

Скрипт создаёт `07_hotwatcher_api.json`, если его ещё нет; API слушает только
`127.0.0.1:10085`, без публикации в LAN/WAN. Xray игнорирует отдельный блок
`hotwatcher`, а Hot Watcher читает из него ссылку подписки.
Если API уже настроен другим инструментом, скрипт **откажется создавать второй объект**.
Тогда объедини `HandlerService` и `RoutingService` в существующем API и проверь
`api_address` в конфиге Hot Watcher: [инструкция](docs/INSTALLATION.md).

Твой `05_routing.json` менять не нужно, если в нём уже есть:

```json
{
  "routing": {
    "balancers": [
      {
        "tag": "proxy",
        "selector": ["main--VL"],
        "strategy": {"type": "leastPing"}
      }
    ]
  }
}
```

Это **только фрагмент для сверки**, не замена твоего полного routing. Списки доменов/IP,
правила `direct`/`block`, `balancerTag: "proxy"` и существующий `burstObservatory` сохраняются.
Никакой `fallbackTag` программа не добавляет.

### 5. Проверить и выполнить первую миграцию

```sh
/opt/sbin/hotwatcher doctor
/opt/sbin/hotwatcher plan
```

`doctor`: ожидается `"ready": true`. Существующие DNS-фрагменты Xray с комментариями
не нужно переписывать ради проверки селектора: Hot Watcher читает маршрутизацию из
`05_routing.json`, а полный набор фрагментов проверяет установленным Xray.
`plan` показывает количество поддерживаемых и
изменившихся узлов; не применяет изменения к Xray и не заменяет его конфигурацию.

Затем:

```sh
/opt/sbin/hotwatcher adopt
/opt/sbin/hotwatcher status
```

`adopt` — **явное разрешение взять под управление `04_outbounds.main.json`**.
Оригинал сохраняется в `/opt/var/lib/hotwatcher/pre-migration-outbounds.json`.
При проверках, не прошедших до стадии API, старый конфиг и выбранный маршрут сохраняются.
При ошибке уже во время применения остаётся `pending.json`; см. `recover`/`abort` ниже.

Новые теги выглядят как `main--VL--hw-<хеш>`. Они соответствуют твоему селектору `main--VL`,
но создаются по реальным параметрам VLESS, а не по наличию букв `VL` в названии.
Старые legacy-теги не удаляются из памяти при первой миграции; после следующего обычного
перезапуска они не загрузятся из заменённого файла. Отдельный старый `04_outbounds.json`
программа не трогает.

### 6. Включить службу — проверка раз в 30 минут

```sh
sh scripts/enable-service.sh
/opt/etc/init.d/S99hotwatcher status
```

Не добавляй параллельный cron. Интервал идёт от запуска службы, не обязательно точно
в `:00` и `:30`. Он настраивается полем `interval_seconds`.

## Повседневные команды

Автоматический выбор DNS для **встроенного DNS Xray** включается отдельно: `hotwatcher dns test`, затем `hotwatcher dns auto on`. После проверки `xkeen -xtest` нужен один ручной `xkeen -restart` вне игры. При каждом DNS-запросе Xray выбирает первый успешный ответ из Cloudflare и Google DoH. Настройка DNS самого Keenetic, DHCP и Karing не меняется; Yandex в списке нет. Откат: `hotwatcher dns auto off` и ручной перезапуск. Условия, ограничения и проверка маршрута: [DNS_AUTO.md](docs/DNS_AUTO.md).

```sh
hotwatcher status          # Состояние, выбранный тег, совпадение runtime/disk
hotwatcher sync            # Проверить подписку сейчас, без рестарта основного Xray
hotwatcher hard-sync       # Если VPN мешает загрузке: временно остановить XKeen и скачать напрямую
hotwatcher recovery status # Этап прерванного hard-sync, блокировка и следующий шаг
hotwatcher recovery resume # Вернуть XKeen и завершить незавершённую транзакцию
hotwatcher recovery abort  # Вернуть XKeen и отменить незавершённое применение
hotwatcher doctor network  # Проверить подписку, API, ключ и DNS по этапам
hotwatcher dns verify      # Проверить текущий DNS-фрагмент отдельным Xray по двум маршрутам
hotwatcher nodes           # Имена и теги узлов, без учётных данных
hotwatcher keys            # Сразу показать все ключи последней загрузки и сохранённые ключи
hotwatcher keys --check    # Заново проверить доступность применённых ключей
hotwatcher update          # Проверить и установить подписанное обновление программы
hotwatcher check-key       # Проверить активный ключ дважды и сменить при отказе
hotwatcher select "VL HLVPN_09-12FIN_2_UNDEF"  # Выбрать по точному имени из keys
hotwatcher stop            # Остановить службу подписки и выбрать статический vless-reality
hotwatcher start           # Вернуть самый быстрый работающий ключ подписки и службу
hotwatcher hold on         # Пауза обновлений/очистки на время игры
hotwatcher hold off        # Снять паузу
hotwatcher gc              # Вне игры: удалить старые управляемые узлы после grace period
```

`keys` сразу показывает сохранённый список и все ключи последней успешно разобранной
подписки, даже если её применение сорвалось или API Xray сейчас недоступен. Для каждого
ключа видно, применён ли он. `keys --check` заново измеряет HTTPS-доступность
применённых ключей и может выполняться несколько минут; это не ICMP-пинг.
Команды просмотра не переключают узлы и не обновляют отметку проверки подписки.

Если обычный `sync` не может скачать подписку из-за сломанного VPN, выполни
`hotwatcher hard-sync` вручную. Команда блокирует операции службы Hot Watcher и останавливает XKeen,
дожидается остановки Xray, скачивает подписку и проверяет ключи напрямую, затем запускает
XKeen и применяет весь список ключей обычной защищённой транзакцией. Недоступные
кандидаты остаются в списке, но не выбираются; если не прошёл ни один, старый набор
сохраняется. Служба Hot Watcher продолжает работать после команды. При ошибке загрузки
старые ключи сохраняются, а XKeen запускается обратно. Эта команда прерывает
текущие VPN-соединения; используй её только когда допустим короткий перерыв.
Если после `xkeen -start` API Xray недоступен, команда сообщает об ошибке и не
применяет подписку; скачанный список всё равно виден в `keys` как не применённый.
Подписка должна быть доступна через прямое соединение роутера.
Если процесс прервался, `recovery status` покажет последний записанный этап и реальную
блокировку процесса. `recovery resume` запустит XKeen при необходимости и завершит
сохранённую транзакцию; `recovery abort` восстановит предыдущий выбор. Новый
`hard-sync` не начнётся поверх незавершённого журнала.

`dns verify` проверяет работу DNS-модуля во **временном** Xray сначала напрямую,
затем через выбранный VLESS. Он не трогает работающий процесс и отдельно сообщает,
доступен ли его API. Проверка не доказывает, что основной Xray уже загрузил новый
DNS-фрагмент после перезапуска; это ограничение отображается в отчёте.

Краткая русская справка: `hotwatcher help`. Редкие команды: `hotwatcher help advanced`.

Для ручного выбора скопируй тег или точное имя из `keys`:

```sh
hotwatcher select main--VL--hw-ХЕШ_ИЗ_NODES
hotwatcher select "VL HLVPN_09-12FIN_2_UNDEF"
```

Это переключает **новые** подключения после проверки кандидата. При смене сервера
новые соединения могут получить другой внешний IP; это не «перенос» существующей сессии.
Если имена двух узлов совпадают, используй тег: неоднозначное имя отклоняется.
`select` проверяет доступность Xray API до создания журнала переключения. При
остановке Xray в ходе транзакции запусти `recover` после его запуска; не удаляй
`pending.json` вручную.

`hotwatcher stop` и `hotwatcher start` переключают маршрут без рестарта основного Xray.
Статический ключ берётся из существующего `04_outbounds.json`; Hot Watcher не изменяет
этот файл. `04_outbounds.main.json` необходим и для узлов подписки, и для устойчивого
статического маршрута после перезапуска Xray. Не удаляй его. Подробности и действия
при отказе статического ключа: [STATIC_FALLBACK.md](docs/STATIC_FALLBACK.md).

## Проверка отсутствия рестарта

```sh
pidof xray
hotwatcher sync
pidof xray
hotwatcher status
tail -n 20 /opt/var/lib/hotwatcher/events.jsonl
```

Сравнивай PID **после завершения** команды: во время health-check временно существует
дополнительный тестовый процесс `xray`. В журнале при применении будет `applied`,
`"restart": false`; при неизменной подписке — `unchanged`. Это не доказывает отсутствие
внешнего рестарта, вызванного другим заданием/администратором.

## Ошибка применения

Не перезапускай Xray автоматически. Сначала:

```sh
hotwatcher status
```

Если `pending_transaction: true`:

```sh
hotwatcher recover         # Повторить/завершить сохранённую транзакцию
# либо, если нужно вернуть состояние до этой попытки:
hotwatcher abort
```

Это альтернативы, а не две команды подряд. `abort` не удаляет уже добавленные handlers
из памяти: ими могли начать пользоваться соединения. Детали и полный откат:
[ROLLBACK.md](docs/ROLLBACK.md).
