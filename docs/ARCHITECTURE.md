# Архитектура и модель отказов

## Граница ответственности

Hot Watcher управляет одним файлом outbounds и одним балансировщиком. Он не является
новым VPN-ядром и при обычной работе не меняет правила маршрутизации ОС и не управляет
firewall. Ручной `hard-sync` вызывает `xkeen -stop` и `xkeen -start`: XKeen сам
управляет остановкой своего процесса и сетевыми правилами. Протокол API реализует уже установленный Xray: приложение вызывает его CLI
`api lso/ado/rmo/bi/bo`, без shell-интерпретации аргументов.

`hard-sync` берёт блокировку операций подписки и проверяет, что нет
незавершённой транзакции или статического режима. После остановки XKeen он ждёт
исчезновения Xray API, загружает подписку прямым HTTPS-соединением и проверяет
её узлы изолированными Xray-процессами без VPN. Недоступные кандидаты сохраняются
в списке, но не выбираются; если все недоступны, старый набор остаётся.
Результаты успешных проверок используются только в текущем применении и затем
удаляются из памяти. XKeen запускается снова даже при ошибке загрузки; доступность
API списка и балансировщика после запуска проверяется до применения. Разобранные
узлы передаются обычной транзакции без повторной загрузки. Отдельный приватный
список имён и тегов позволяет `keys` показать загруженные узлы после отказа API.
Это намеренно прерывает текущие VPN-соединения и не является автоматическим fallback.

```text
HTTPS URI subscription -> parser + content hashes -> candidate Xray config test
                                                   -> isolated end-to-end probes
                                                               |
private transaction journal <-----------------------------------+
        |
API: pin old -> add new -> verify list -> pin new -> verify pin
        |
atomic replace generated outbounds -> atomic replace state -> remove journal
        |
retired owned outbounds stay in memory; explicit gc after grace
```

## Идентичность узла

`tag = main--VL--hw- + SHA256(canonical outbound without tag)[0:24]`.
В содержимое хеша входят учётные параметры, адрес, порт, транспорт, SNI и настройки
защиты. Перестановка строк подписки, дублирование одинаковых URI или смена только имени
не вызывает замену узла. JSON-кодирование Go детерминирует порядок строковых ключей.

Дополнительно вычисляется endpoint identity без UUID/Reality public key/отображаемого
имени: адрес, порт, транспорт, security, SNI, path/serviceName. Она используется только
как предпочтение при ротации ключа, не как доказательство одинакового внешнего IP.

## Выбор узла по задержке HTTPS через VLESS

При `selection_policy: latency` каждый sync проверяет все узлы отдельным процессом
Xray с HTTP-входом только на loopback и измеряет время успешного HTTPS-ответа 204.
Самый быстрый доступный узел закрепляется через проверенный `RoutingService` override.
Проверка запускается и при неизменной подписке. При отказе всех известных узлов
сохраняется прежняя фиксация. Недоступные узлы остаются в списке, но не выбираются;
их работоспособность повторно проверяется при будущих выборах. Переход может
изменить внешний IP новых подключений.

`selection_policy: sticky` оставляет прежний алгоритм:

1. Если выбранный tag остаётся в новом списке — сохранить его.
2. Если tag исчез, предпочесть новый узел с той же endpoint identity.
3. Иначе применить `preferred_name_contains`.
4. Иначе выбрать детерминированно первый узел из сортировки по tag.

`RoutingService` override имеет приоритет над обычным выбором стратегии.
Пока override установлен, одноимённый `proxy` балансировщик закреплён за одним узлом.

`leastPing`/Observatory остаются в исходном конфиге: программа не редактирует routing.
Проверки Observatory могут продолжаться, но не переключают закреплённый target.
При необходимости оператор может выполнить `nodes` и `select TAG`.
Команда `keys` быстро показывает последний загруженный список и сохранённые ключи без
обращения к Xray API. Выбранный по сохранённому состоянию ключ идёт первым.
Команда `keys --check` измеряет свежую задержку применённых ключей без записи в Xray API.
Отметка `selected_at` меняется только при выборе другого ключа;
`last-check.json` хранит время последней попытки проверки подписки, а не запуска `keys`.
У состояния старых версий точное время предыдущей смены ключа неизвестно.

## Первая миграция

`adopt` требует рабочую текущую выборку балансировщика: через API должно быть видно,
какой существующий outbound можно закрепить перед добавлением нового пула. Если выборка
пустая, миграция не проводится вслепую. Проверяются селекторы из локальных JSON.

Legacy outbounds не считаются собственностью нового инструмента. Они не удаляются
через API при `adopt`, даже если их записи уже заменены в генерируемом файле. Это позволяет
не закрывать их сразу при переходе. Они исчезнут из нового процесса после будущего
перезапуска; специально перезапускать ради очистки во время игры не надо.

## Подготовка, применение, фиксация

До записи journal выполняются: download -> parse -> limits -> current disk hash -> API
availability -> выбор target -> `xray run -test` полного временного набора конфигов ->
проверка узлов для выбора рабочего target. Недоступные узлы не становятся
выбранным маршрутом, но остаются в конфигурации для будущих проверок.

По умолчанию проверка кандидата использует работающий Xray: API временно добавляет
outbound с тегом вне production selector, HTTP-вход с паролем на loopback и
правило routing к нему. Параллельно создаётся заблокированный контрольный
маршрут: успешный ответ через него означает, что более раннее правило перехватило
проверку, и такой результат отклоняется. `adrules` вызывается только с `-append`: существующие
правила и balancer не заменяются. После HTTP 204/URL Test вход, правило и выход
удаляются. Текущий balancer не переключается до успешного завершения транзакции.
При отключённой галочке Web UI используется прежний отдельный пробный Xray.
TLS-проверка сертификатов включена. Успешный TCP/HTTPS probe **не является
проверкой игрового UDP**.

Далее записывается `pending.json` (fsync), фиксируется старый target, добавляются новые
outbounds, проверяется их присутствие через `lso`, выбирается и проверяется новый target.
Только после этого атомарно заменяются генерируемый файл и `state.json`.

Запись одного файла атомарна через rename в той же файловой системе и fsync каталога.
**gRPC и файловая система не образуют единую атомарную транзакцию.** Журнал нужен именно
для промежутка между изменением runtime и сохранением файлов.

## Отказы

| Этап | Поведение |
|---|---|
| Загрузка/парсер/валидация/probe | Никаких добавлений или переключений; старый файл остаётся |
| Частичное `ado` | Старый target остаётся закреплённым; новые handlers могут уже присутствовать; journal сохраняется |
| Ошибка `bo`/его подтверждения | Не утверждается, что переключение не состоялось; остаётся journal |
| Runtime переключён, запись на диск не удалась | Не рестартовать Xray; `recover` завершает фиксацию |
| Диск изменён чужим updater-ом | Проверка хеша останавливает применение/восстановление |
| Все новые кандидаты не проходят probe | Старый пул остаётся; нет «пустого» обновления |
| Превышен лимит retired | Новое обновление отклоняется до ручной очистки |

`recover` идемпотентно добавляет отсутствующие staged nodes, заново проверяет выбранный
кандидат, закрепляет target и фиксирует диск/state. Неподтверждённая транзакция не
продолжается автоматически службой.

`abort` возвращает предыдущие файл/state/target. Добавленные в неудачной транзакции
узлы не удаляются: через них уже могли начать идти соединения. Такие orphan handlers
уйдут при плановом перезапуске; автоматический массовый поиск и удаление не выполняется.

## Старые соединения и очистка

Retired outbounds исключены из новой политики выбора за счёт pin, но остаются в менеджере.
Они не сохраняются в новом файле outbounds: после reboot уже не будут созданы.

В просмотренном коде Xray `RemoveHandler` удаляет запись менеджера без вызова `Close()`.
Это полезное свойство текущей реализации, но не контракт сохранения любой UDP/Mux-сессии
и не обещание совместимости будущих версий. Поэтому `automatic_gc = false` по умолчанию.
`gc` удаляет только записанные в state собственные retired tags после `grace_seconds`.

## Перезапуск роутера/ядра

Runtime override не хранится самим Xray в JSON. После запуска Hot Watcher сверяет
сохранённый pool и pin через API. Демон делает это каждые `reconcile_seconds`.
Пока API недоступен или до восстановления pin действует исходная стратегия Xray.
**В этом окне нет гарантии выбранного узла и нет независимого kill-switch.**

Локальная блокировка `flock` предотвращает одновременные изменения от двух команд
Hot Watcher. От другого приложения защищает только проверка хеша перед применением;
она не делает безопасной совместную запись одним файлом. Владельцем должен быть один
updater, поэтому cron старого watcher отключается до миграции.
